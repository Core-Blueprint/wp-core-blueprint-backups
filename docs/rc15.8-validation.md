# RC15.8 restore completion

## Problem and behavior

After migration invalidates a WordPress session, the monitor stopped polling on `auth_required`. WordPress interim login hides its modal without reloading the page. The stopped monitor had no listener for that transition, and its nonce belonged to the old session. Terminal jobs were also omitted from the PHP page, leaving completion dependent on a one-shot recovery request and a transient toast.

RC15.8 keeps explicitly requested terminal jobs in the server-rendered panel. Successful, failed and cancelled outcomes remain visible after reload. A remembered job ID in session storage recovers the same job when returning without its query parameter; the server must still authorize and validate every status request. Storage denial leaves the current job recoverable through its URL.

The monitor observes WordPress' auth-modal visibility change with vanilla JavaScript, then probes the authenticated endpoint. Closing the modal alone does not imply successful authentication or completion. Authorized nonce expiry refreshes the page once; repeated failures expose a manual retry instead of looping. Permission loss remains an explicit unconfirmed monitoring state. No unauthenticated status disclosure, capability bypass, or automatic privileged-user approval is added.

The restore worker no longer regenerates rewrite rules using possibly pre-switch registrations. It deletes that runtime cache; WordPress regenerates it from the restored runtime on a fresh request.

## Data comparison that motivated this patch

The supplied phpMyAdmin dumps contained 203 active-prefix tables on each side. Their column definitions matched. After independently applying expected URL/prefix transformations, 196 tables matched exactly; the seven differences were job state, options, audit events, user metadata, and three Wordfence activity/configuration tables. The destination recorded a completed restore with 202 tables passing pre-commit content verification; the operational job table is retained separately.

The source additionally contained 115 tables under another prefix and ended with phpMyAdmin error #2006 before its index/constraint section. It is therefore insufficient for a complete source index/constraint comparison. The later destination download screenshot reports the same rounded size; its new SQL bytes were not supplied and are not claimed to have been compared.

The destination audit records four privileged-access reviews. The four source approval fingerprints match their destination review fingerprints. Base's signed approvals depend on the site auth salt; this is consistent with destination signatures becoming invalid, but salts were not supplied for direct verification. Approvals must follow the existing Base trust/recovery process. This patch neither re-signs approvals nor weakens the guard.

## Regression coverage

- PHP execution tests: denied capability plus stale nonce, nonce denial, authenticated outcome, missing job, unauthenticated request, persistent Completed rendering, failed result despite a success query flag, and active-job selection.
- Chromium tests run the shipped JavaScript with controlled AJAX responses: completion, interim-login recovery, dismissed login, revoked permission, nonce refresh/loop prevention, maintenance response retry, terminal page, pending-job recovery, failed recovery, visible recovery errors, disabled storage, and absence of any pending job.
- The existing MySQL/MariaDB database engine E2E additionally checks that same-site and migration completion leave rewrite regeneration to a fresh request. Existing fidelity and rollback gates remain unchanged.

## Acceptance boundary

The observed real-site restore completed before this patch. Patched UI acceptance still requires testing WordPress interim login and the actual Base permission state on the disposable destination. A success panel cannot be shown to an account that Base currently forbids from reading Backups. This is not a restore-engine failure, and must not be hidden by inventing a success response.

PR #4 remains unmerged. Full Backups/Beacon/Hub acceptance and the RC15.6 remaining release gates are not waived.
