# RC15.6 validation and release gates

## Implemented scope

- A: shared WordPress SQL codec; percent preservation in exporter and transformer; explicit exporter read failures.
- B: source-derived per-table schema/row counts/content digests; migration source validation; target expectations from values before encoding; shadow content verification required by both live-commit entry points.
- C: request-independent configured site identity (including HTTPS under CLI), bounded INSERT bytes, session SQL-mode restoration, exporter checkpoint truncation/replay and targeted robustness coverage.

No vendor/builder-specific transformation code was copied from the reference plugins. The shadow/atomic-rename/recovery architecture is retained.

## Automated evidence

The `Database fidelity` workflow runs on disposable MySQL 8.0 and MariaDB 10.11 with PHP 8.4 and official WordPress 7.0. It calls the real WordPress database implementation; it does not substitute a prepare mock for integration assertions.

`database-roundtrip.php` compares source and shadow/live values exactly: percent/CSS/permalink patterns, quotes/backslashes, NUL/CR/LF, UTF-8/emoji, NULL versus empty, JSON, escaped URLs, nested serialization, a large serialized array, large longtext and every byte value in BLOBs. Migration expectations are separately specified fixture values. A same-row-count mutation must fail before live commit. Tests also exercise same-site commit/rollback, migration commit, rejected source-digest mismatch and an injected SELECT error.

`database-robustness.php` exercises numeric/string/composite/binary/no primary keys, an empty table, duplicate rows, large integer/decimal values, more than 2,000 rows per key strategy, INSERT byte boundaries and a simulated lower destination packet limit. It tests a lost exporter acknowledgement, lost digest-merge acknowledgement, and a no-PK import replay that must fail closed rather than become Completed. Digest results must agree across different chunking and row orders.

`database-engine-e2e.php` drives actual database job storage and Runner/Backup/Restore engines through archive creation, verification, extraction, shadow verification, live commit and Completed. It performs same-site recovery and URL/prefix migration, then checks independently expected values, GUID preservation, role/capability keys and maintenance cleanup. It deliberately does not invoke Base activation or claim full-site/remote coverage.

PHP lint and the existing migration/filesystem smoke tests remain separate gates. The final commit's GitHub Actions results are the authoritative execution evidence; merely adding a test is not a PASS.

## Remaining acceptance before merge/product release

- Disposable full-site same-site and migration restores with the actual compatible Base, plugin activation, UI, filesystem switching and critical recovery.
- Beacon/Hub remote transfer, cancellation, retry and deployment safety-gate acceptance. No remote trust-status semantics were upgraded by this patch.
- Broader disk-full/short-write, PHP termination and cross-component rollback fault injection. Current targeted replay tests are not exhaustive crash testing.
- A product decision and evidence for application-consistent snapshots while source database/files change. Digests prove the captured values, not a single global moment in time.
- Performance/resource acceptance with representative large production-shaped datasets; OFFSET/hash ordering on no-PK tables and external digest runs cost time/disk. Fetch batch row limits do not impose a hard PHP byte-memory ceiling for unusually large rows.
- Additional compatibility coverage for collations, custom serialization/opaque payloads, schema variants and overlapping URL mappings. Unsupported schema/packet conditions must not be silently downgraded.

Keep PR #4 open and unmerged until required acceptance is recorded. Production and golden-source staging are not destructive test targets. RC15.5 archives lacking the new metadata cannot bypass the preflight gate; create new backups from a healthy source after updating. Do not update the runtime during an active backup/restore job.

Archive verified means checksum verification. Restore-tested means a recorded successful recovery rehearsal; the latter is not inferred from the former.
